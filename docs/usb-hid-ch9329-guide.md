# USB 硬件键鼠（CH9329）测试与开发指南

> 状态：这块单头模块已在 macOS 26 上冒烟通过，USB 字符串已写成 `BORUI` / `BR-K206 KM Combo`（2026-10-22，见 4.4）。应用设置里的可选输入叫「USB 助理」：串口在、并且读信息帧确认 USB 已枚举时才能选。选中后移动、点击和快捷键走串口；打不开或没有应答就停下来说明，不会改回软件键鼠。接入时踩过的坑见第 6 节。
> 协议细节来自 WCH 公开资料与社区实践，具体以模块附带的《CH9329 芯片串口通信协议》手册为准。

## 1. 背景与结论

识流（thiflow）售卖的“USB 机器人”（约 99 元）本质是一个**串口转 USB HID 键鼠**的硬件。软件仍然截图 + VLM 识别，只是把“移动鼠标 / 点击 / 按键”从系统 API 改成发串口指令，由硬件以真实 USB 键盘鼠标的身份输入。

| 问题 | 结论 |
| --- | --- |
| 技术可行性 | 可行，方案成熟（KVM、自动化测试常用），成本 10–40 元 |
| 能防什么 | Windows 下 `SendInput` / robotjs 产生的事件带 `LLMHF_INJECTED` / `LLKHF_INJECTED` 标记，可被低级钩子识别；硬件 HID 输入没有这个标记，设备枚举上也是普通键鼠 |
| 防不了什么 | 行为层风控：回复速度过快、24 小时在线、话术高度重复、短时间大量加好友/群发、账号环境（IP、设备）异常。这些和输入方式无关 |
| 云桌面 | **不适用**。云桌面没有物理 USB，键鼠来自远程协议，本身就是虚拟输入。要用硬件方案必须是物理 Windows 机 |
| 合规提醒 | 自动化操作微信违反微信软件许可协议，硬件方案只降低“被识别为模拟输入”的概率，不改变账号风险 |

最可能的技术栈：CH9329（HID）+ CH340G（USB 转串口）+ USB Hub 芯片合在一个插头里；PC 端软件通过串口发 CH9329 协议帧；中文输入用“写剪贴板 + 硬件 Ctrl+V”，绕开键盘无法直接打中文的问题。

## 2. 硬件说明

- **CH9329**：串口（UART）进，USB HID 键盘/鼠标出。PC 看到的是一个标准键鼠。
- **CH340G**：USB 转串口芯片，让 PC 能通过 USB 给 CH9329 发串口数据。
- **单头模块**：两颗芯片经内置 Hub 共用一个 USB 插头。插上后 PC 同时看到：1 个串口设备 + 1 个 HID 键鼠（部分模块是复合设备）。
- 对比：天猫上 12 元左右的是裸 CH9329 TTL 模块，需要另配 USB-TTL 转接板，占两个 USB 口，接线 TX↔RX 交叉、共地。

### 设备识别

| 系统 | 串口名 | 驱动 |
| --- | --- | --- |
| Windows | 设备管理器 → 端口 → `USB-SERIAL CH340 (COMx)` | Win10/11 多数自动装；没有就装 WCH 官方 CH341SER |
| macOS | `/dev/cu.wchusbserial*` 或 `/dev/cu.usbserial-*` | macOS 11+ 自带 |

macOS 查看：`ls /dev/cu.*`，插拔前后对比。

## 3. CH9329 串口协议速查

- 默认串口参数：**9600 bps，8N1**（可通过配置命令改，改后需重新上电）。
- 帧格式：

```
HEAD(2)   ADDR(1)  CMD(1)  LEN(1)  DATA(LEN)  SUM(1)
57 AB     00       xx      xx      ...        前面所有字节相加取低 8 位
```

- 芯片应答：CMD 为 `原 CMD | 0x80` 表示成功，`原 CMD | 0xC0` 表示出错。

| CMD | 用途 | DATA |
| --- | --- | --- |
| `0x01` | 读芯片信息（版本、USB 枚举状态、指示灯） | 无 |
| `0x02` | 普通键盘 | 8 字节：`修饰键, 00, k1..k6`（标准 HID 键码） |
| `0x03` | 多媒体键 | — |
| `0x04` | 绝对鼠标 | 7 字节：`02, 按键, X低, X高, Y低, Y高, 滚轮`；X/Y 范围 0–4095 |
| `0x05` | 相对鼠标 | 5 字节：`01, 按键, dx, dy, 滚轮`（有符号 -127..127） |
| `0x08` / `0x09` | 读 / 写 50 字节参数（模式、波特率、VID/PID、字符串使能） | 写的时候模式字节只能是 `0x00`–`0x03` / `0x00`–`0x02` |
| `0x0A` / `0x0B` | 读 / 写 USB 字符串 | 第 1 字节类型：`0x00` 厂商、`0x01` 产品、`0x02` 序列号；接着 1 字节长度和最多 23 字节内容 |
| `0x0C` | 参数和字符串恢复出厂 | 无 |
| `0x0F` | 软复位 | 无。新字符串要复位或重新上电后，系统才看得到 |

常用值：

- 修饰键位：`0x01` 左 Ctrl，`0x02` 左 Shift，`0x04` 左 Alt，`0x08` 左 Win/Cmd。
- 键码：`V = 0x19`，`Enter = 0x28`，`Backspace = 0x2A`，`A = 0x04`。
- 鼠标按键位：`0x01` 左键，`0x02` 右键，`0x04` 中键。
- **按下后必须发一帧全 0 表示松开**。键盘释放帧：`57 AB 00 02 08 00 00 00 00 00 00 00 00 0C`。

绝对坐标换算（推荐，用它点击最准）：

```
hidX = round(x / screenWidth  * 4095)
hidY = round(y / screenHeight * 4095)
```

应用里实际用的是 `Math.floor((4096 * 坐标) / 轴长)`。2026-10-22 在这台 Mac 的 1800×1169 上，`(120, 80)` 得到 `273, 280`，和光标对准。上面的 `round(* 4095)` 会差零点几个像素。

注意 Windows 缩放（125%/150%）：截图坐标和 HID 坐标都按**物理分辨率**算，别混用逻辑像素。多显示器时绝对坐标通常映射到主屏，点到主屏外面这次直接拒绝。

## 4. 测试步骤（拿到硬件后）

### 4.1 冒烟测试

1. 插上模块，确认串口出现（见第 2 节），且系统里多了一个 HID 键鼠。
2. 用串口调试工具（Windows：SSCOM / WCH 串口助手；Mac：CoolTerm）9600 8N1，十六进制发送：
   - 读信息：`57 AB 00 01 00 03`，应收到 `57 AB 00 81 ...` 开头的应答。
   - 打字母 a：先发 `57 AB 00 02 08 00 00 04 00 00 00 00 00 10`，再发释放帧。光标处应出现 `a`。
3. 都通过说明硬件、驱动、波特率没问题。

### 4.2 脚本测试（Node）

在仓库外建临时目录跑，避免污染依赖：

```bash
mkdir ~/ch9329-test && cd ~/ch9329-test && npm init -y && npm i serialport
```

`test.mjs`：

```js
import { SerialPort } from 'serialport'
const port = new SerialPort({ path: process.argv[2], baudRate: 9600 })
const frame = (cmd, data = []) => {
  const b = [0x57, 0xab, 0x00, cmd, data.length, ...data]
  return Buffer.from([...b, b.reduce((s, x) => s + x, 0) & 0xff])
}
const sleep = (ms) => new Promise((r) => setTimeout(r, ms))
const key = async (mod, code) => {
  port.write(frame(0x02, [mod, 0, code, 0, 0, 0, 0, 0])); await sleep(40)
  port.write(frame(0x02, [0, 0, 0, 0, 0, 0, 0, 0])); await sleep(40)
}
const absMove = async (x, y, W, H, btn = 0) => {
  const hx = Math.round((x / W) * 4095), hy = Math.round((y / H) * 4095)
  port.write(frame(0x04, [0x02, btn, hx & 0xff, hx >> 8, hy & 0xff, hy >> 8, 0])); await sleep(30)
}
port.on('data', (d) => console.log('<<', d.toString('hex')))
port.on('open', async () => {
  port.write(frame(0x01)); await sleep(200)          // 读信息
  await absMove(960, 540, 1920, 1080)                 // 移到屏幕中心（按实际分辨率改）
  await absMove(960, 540, 1920, 1080, 0x01)           // 左键按下
  await absMove(960, 540, 1920, 1080, 0x00)           // 松开
  await key(0x01, 0x19)                               // Ctrl+V（Mac 用 0x08 = Cmd）
  await key(0x00, 0x28)                               // Enter
  port.close()
})
```

运行：`node test.mjs COM3`（Windows）或 `node test.mjs /dev/cu.wchusbserial110`（Mac）。

### 4.4 改 USB 字符串（2026-10-22，这块模块已写完）

沁恒的图形配置软件是 Windows 程序。写入本身是串口帧，Mac 能直接写，不需要那个软件，也不需要卖家预先烧录。配置存在芯片里，断电还在。

这块模块当时的串口是 `/dev/cu.usbserial-11140`，9600 8N1。写完并软复位后，系统枚举为：

| 字段 | 写入前 | 写入后 |
| --- | --- | --- |
| 厂商字符串 | `WWW.WCH.CN` | `BORUI` |
| 产品字符串 | `WCH UART TO KB-MS_V1.8` | `BR-K206 KM Combo` |
| 序列号 | `20194152DBBD` | `20194152DBBD`（未改成另一台设备的号） |
| VID / PID | `0x1A86` / `0xE129` | 未改 |

`BORUI` / `BR-K206` 是自拟的白牌名，不是在售牌子。每条字符串最多 23 字节。

操作顺序：

1. `0x08` 读出 50 字节参数，`0x0A` 读出三条字符串。
2. 写参数时，把读回来的工作模式 `0x80`、通信模式 `0x80` 改成 `0x00`、`0x00`。这两个 `0x80` 表示「由引脚决定、当前是模式 0」；`0x09` 只接受软件设置值 `0x00`–`0x03` 和 `0x00`–`0x02`。功能不变：普通键盘 + 多媒体键 + 绝对/相对鼠标，协议传输，波特率仍是 9600。
3. 参数第 37 个字节（从 0 起算是下标 36）是字符串使能。写成 `0x86`：bit7 总开关，bit2 厂商，bit1 产品。没有单独打开 bit0。
4. `0x0B` 写厂商 `BORUI`、产品 `BR-K206 KM Combo`。使能位先打开、再写字符串，然后发 `0x0F` 软复位，系统里才会同时变成新名字。先写字符串再开使能时，产品名会变，厂商名仍可能停在 `WWW.WCH.CN`，需要在使能打开后再写一次厂商并复位。
5. 打开自定义字符串后，USB 序列号改走芯片里保存的那一槽，不再用内部序号。这一槽出厂内容是占位符 `20190215xxxx`，枚举会变成这串占位符。要保持原来的 `20194152DBBD`，把该槽写成这个值。自定义序列号位虽然没单独打开，枚举仍使用了槽里的内容。

VID/PID 没动。报告描述符也没变，仍是这块芯片的键盘 + 相对鼠标 + 13 位绝对鼠标。恢复出厂可以发 `0x0C`，或把 DEF 引脚拉低 3 秒以上。

## 5. 接入 SightFlow 的开发方案

### 现状

截图和识别仍走原流程。键鼠动作集中在 `src/core/rpa/input-utils.ts`，经 `src/core/rpa/input-driver.ts` 分到软件键鼠或 USB 助理。帧的拼装在 `src/core/rpa/ch9329.ts`，不打开串口。

- 拟人轨迹保留。USB 模式下每一步是一帧绝对坐标，帧间隔至少 20 ms。
- 光标位置仍用 robotjs 读取。这一步不产生注入事件，硬件也读不回光标。
- 坐标用 `Math.floor((4096 * 坐标) / 轴长)`，轴长与 robotjs 同一套：macOS 逻辑像素，Windows 物理像素。点不在主屏上时直接拒绝，提示「副屏这次不点」。
- 中文仍是剪贴板加一次硬件粘贴（Mac 为 Command+V，Windows 为 Ctrl+V）。分段和错字规则不变。
- 设置页用「软件键鼠 / USB 助理」。界面不写芯片型号，也不叫「机器人」或「USB 键鼠」。串口每次用 `SerialPort.list()` 现找：厂商 `1a86` 产品 `7523`，或路径含 `usbserial` / `wchusbserial`，排除蓝牙。不把端口号写进配置。
- 只有找到串口，并且读信息应答的第 2 个数据字节是 `0x01`，单选才可点。没找到时保持软件键鼠。已经选中之后如果断开，选项仍停在 USB 助理，这一条不会改走软件注入。
- 打开失败、超时或应答状态不是成功时，停掉这一次发送并把原因告诉用户。写完成之前到达的帧不算这一次的应答。松开帧失败时，下一次动作先发全 0。手势还在走时不做串口探测；这时改回软件键鼠，后面的拐点不再打开串口。

### 依赖与打包注意

- `serialport` 是原生模块。安装后的 `postinstall` 会跑 `electron-builder install-app-deps`，按 Electron 39 的 ABI 重新编译。`electron-builder.yml` 的 `asarUnpack` 包含 `serialport` 和 `@serialport`。
- 键盘布局：HID 键码是物理键位，非美式布局下字母可能不同；中文一律走剪贴板，避免依赖输入法状态。粘贴前确保输入法不会吞掉 Ctrl+V（一般没问题，测试时留意）。
- 节奏：每帧之间留 20–50 ms；9600 bps 下一帧 14 字节约 15 ms，不要连发过快。需要更快可把波特率改到 115200。

## 6. 接入时踩过的坑（2026-10-22 ～ 2026-10-23）

下面是这块模块接到 ChatBuddy 当天实际碰到的情况。协议表在第 3 节，字符串写入顺序在 4.4。

### 6.1 插上以后系统在干什么

- macOS 会弹出键盘设置助理，设备名当时是 `WWW.WCH.CN`。模块没有物理键，助理里对不上也正常。关掉助理之后，键盘和鼠标帧仍然有效。改完字符串再软复位，助理可能再弹一次。
- 系统能读到 USB 厂商名和产品名。报告描述符不能靠字符串命令改写。VID/PID 保持 `0x1A86` / `0xE129`，不要改成罗技或其他在售牌子。
- `SerialPort.list()` 在 Mac 上经常先给出 `/dev/tty.usbserial-*`。打开 `tty` 会等载波，探测像卡住。用同名的 `/dev/cu.usbserial-*`。后缀随插拔变化，不要写死 `11140`。
- Electron 已经打开这个口时，第二个进程再开会失败。临时验证要写已有的文件描述符，或者先退出应用。不要走正式发送路径做粘贴试验：那条路径点的是存好的微信输入框坐标，粘贴后还会按 Enter。

### 6.2 坐标和点击

- 相对鼠标（`0x05`）会被 macOS 加速，不能用来点准。只用绝对鼠标（`0x04`）。
- 绝对帧同时带坐标和按键。点击帧如果坐标是 0，光标会朝左上角跳。先用 robotjs 读当前光标，换成 HID 坐标记下来，按下和松开都带这个坐标。
- 这台 Mac 的光标空间是 1800×1169 逻辑点，不是面板物理像素。和 robotjs、截图用同一套轴。Windows 用物理像素。先减去屏幕原点，再做第 3 节的整数除法。
- 2026-10-22 把光标移到当前位置，偏差约 1 像素。`(120, 80)` 按 `floor((4096 * 坐标) / 轴长)` 得到 `273, 280`。`round(坐标 / 轴长 * 4095)` 会偏零点几个像素。
- 目标点在主屏外就拒绝，提示「副屏这次不点」。贝塞尔中间点可以夹回主屏，目标点本身先检查。

### 6.3 中文和输入法

- 这台 Mac 的输入法是微信拼音（`com.tencent.inputmethod.wetype`）。HID 直接发字母会被预编辑吃掉，文本编辑里曾经只落下一个 `a`。
- 中文走剪贴板，再发一帧硬件粘贴：Mac 是左 Command + V，Windows 是左 Ctrl + V。不要用 HID 逐字打中文。
- 应用里实际会用到的键只有 `a`、`v`、Enter、Backspace，外加 Command/Ctrl。按下和松开是两帧，按住大约 40 ms。不认识的键直接失败，不要悄悄改发别的键。

### 6.4 串口事务

- 成功应答的命令字是 `原命令 | 0x80`，出错是 `| 0xC0`。动作帧还要看数据首字节，不是 `0x00` 就当没执行。读信息那帧例外：第 2 个数据字节 `0x01` 才是 USB 已枚举。现场读到的开头是 `57 AB 00 81 08 38 01`，`0x38` 是固件 V1.8。
- 同一时间只等一帧应答。鼠标全是 `0x04`，键盘全是 `0x02`，应答里没有序号。超时把等待清掉之后，迟到的按下应答会和后面的松开帧命令字相同，被当成松开已经成功。处理：这次 `write` 回调之前到达的字节一律丢掉，超时同时清接收缓冲。9600 下 14 字节约 15 ms，正常应答不会早于写完成回调。
- 帧间隔至少 20 ms，在驱动里等，不要只靠贝塞尔那 2 ms。等应答大约 450 ms。
- 松开帧失败时，芯片保持上一份键盘报告。`hupcl: false` 是为了关口时不要把已经枚举的键鼠复位，所以关口本身也不会松键。下一次 USB 动作先发键盘全 0；有记下的坐标时再发一帧按键为 0 的绝对鼠标。关链路之前同样先发。修饰键的本地记录要等应答成功再改。
- 贝塞尔每个拐点之间会放开串口锁。若在半路上把设置改回软件键鼠，只改标志并去关口，下一步仍拿着原来的 USB 驱动，会把口再次打开。每个动作进锁后再看一次当前是不是 USB 助理，已经不是就停住，不要换软件驱动把这下点完。
- 主界面大约每 4 秒探测一次，探测里有 `SerialPort.list()`，在 Mac 上常常要几百毫秒，而且和点击共用一把锁。拐点之间的停顿在锁外面，探测会插进来，光标顿一下。移动或点击这一整段手势里跳过探测。串口出错时清掉「已就绪」，并立刻把状态推到界面，不要等下一轮 4 秒。

### 6.5 进程、日志和工作记忆

- `serialport` 13 自带的 N-API 预编译包能在 Electron 39 里直接加载。不要为了它去整包重编原生模块，robotjs 会一起被弄坏。打包时把 `serialport` 和 `@serialport` 放进 `asarUnpack`。驱动里用运行时 `require('serialport')`，避免把原生模块打进主进程包。
- 开发时 electron-vite 经常不重编主进程。只改渲染层时，顶栏可以已经显示「USB 已插上，已激活」，运行日志却还是旧包，没有标记。这不表示退回了软件键鼠。主进程里的发送、轨迹字段和日志前缀，都要等 Electron 重新加载 `out/main` 之后才生效。
- `App.tsx` 热更新会整页刷新，因为 `showToast` 不能快速刷新。屏幕上的运行日志会被清掉，状态灯回到待命，主进程里的引擎循环不一定还在。开发日志的标准输出里没有界面上的那句回复；能对上的是 `[sendReplyAction] 使用缓存输入框坐标`，并且没有失败行。
- 顶栏三态：没插上；插上了但没选；选中并且读信息确认已枚举。只有鼠标尝试、发出的回复和发送失败打标记。布局识别和「正在分析聊天内容」不加。
- 标记在主进程里是全角前缀 `［USB］` 加一个空格。界面把这段剥掉，画 U 盘图标，不画「USB」三个字母，也不用三叉戟符号。
- 工作记忆只在 `phase` 为动作、且动作是点击或发送时写入 `inputDevice: "usb"`。观察、判断、验证、测量、等待不写。点击轨迹是在真正点击之前落盘的，当时的输入模式就是即将使用的设备。`TraceRecorder` 必须把这个字段抄进 `trace.jsonl`，否则会丢。更早的会话没有这个字段，不要回填。

## 7. 风险与边界

- 硬件只解决“输入是否来自真实设备”，行为层风控仍需靠软件侧：随机延迟、工作时间段、频率上限、话术多样化、人工接管。
- 一台模块只能控制它插着的那台电脑，横向扩展意味着每个账号一台物理机 + 一个模块，成本和运维与云桌面方案差别很大，需按规模评估。
- 云桌面场景继续用软件输入，风控重点放在行为层。
