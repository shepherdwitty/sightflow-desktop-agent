# ChatBuddy 1.0 产品需求文档

- 代号：1.0
- 状态：方向已确认，待开发
- 日期：2026-10-21
- 产品：ChatBuddy（界面品牌）。代码基线是 SightFlow 桌面端开源仓库的 fork，安装包名仍为 SightFlow。
- 读者：产品、客户端、网关。本文只定 1.0 要做什么、做到什么算完，不写实现方案。
- 对照材料：`docs/thiflow-vs-sightflow-features.md`。识流清单用于划边界，1.0 不对齐它的企业中台。

## 1. 要解决的问题

号的主人在微信或企业微信里接待已经进来的咨询。人不在键盘前时，回复仍然要像本人、符合手头资料、该停就停。

现在这条链路能看窗口、能点能发，经验卡片和用量账本也在本地。它还不能当班：

- 每一轮几乎只看当前截图，换一句就忘了刚才答应过什么。
- 发送是整段粘贴后立刻回车。三四十个字瞬间出现，看起来不像这个人在打字。
- 遇到不该回的人、群里没 @ 的消息、要人工接手的对话，没有闸门。
- 价格、地址、课程内容写在一段提示词里，资料一多就靠模型临场发挥。
- 设置页能看到具体模型和供应商。商业化之后，用户不需要知道后面接的是哪一家。

1.0 把这件事收成一个岗位：一个微信号上的当班客服。资料和会话留在这台电脑上。商业版只在推理那一跳加网关。

## 2. 产品定义

ChatBuddy 1.0 是运行在用户自己电脑上的桌面当班助手。它看微信或企业微信的当前会话，按本机的人设和资料起草回复，用这个人设定的节奏操作键鼠，并在越界时把这一会话交给人。

一台电脑、同一个时间，只值一个 IM 窗口的班。

1.0 交付四个结果：

1. 看懂当前会话里对方说了什么。
2. 按本机资料和最近对话回复，资料里没有的事实不编。
3. 用可配置的节奏打字、移动鼠标、点击和发送。
4. 命中边界时暂停这一会话，并通知指定的人。

## 3. 四条硬约束

下面四条是需求，不是说明文字。后续切片若与它们冲突，以本节为准。

### 3.1 岗位是客服和售前

服务对象是已经开口的咨询：营业时间、地址、价目、能不能约、课程适合谁、包含什么、怎么买、团队里重复出现的用法和发货问题。

1.0 的动作从「对方来了消息」或「人在当前会话点了发送」开始。沉默客户、未开口的名单、朋友圈和加好友请求，不进入自动动作。

### 3.2 知识库和上下文在本机完成

提示词、知识文件、切块和检索、会话记录、经验卡片、黑白名单、转人工规则、真人节奏、班报，都落在本机用户目录。

换电脑的方式是拷贝这一份本地岗位包，不提供云端同步、云端配置下发、云端知识库。

商业网关不保存知识库，也不充当会话主库。网关可以记扣费需要的次数、token 和时间。

看屏这一步仍要把当次画面交给视觉能力，否则无法读界面。这不等于把知识库上传。画面只服务这一次识别，不进入知识库。

### 3.3 前端不出现模型名字

用户界面、通知、错误提示、确认卡里不出现模型商品名、供应商名字和模型 ID。

用户能看到的连接状态只有两项：看屏是否可用，回复是否可用。

- 开源构建可以继续自己填写 Key，这是开发者路径。
- 商业构建隐藏 Provider、模型、Key 和 token 单价。推理请求发到 ChatBuddy 网关。网关在服务端选择模型。
- 用量账本可以继续在本地记录 token，供排障。商业包默认不在界面展示 token 和费用明细。现有 `SHOW_TOKEN_COST` 开关保持这个方向。

### 3.4 允许故意不走最快路径

每个智能体有一套真人节奏。用户可以把它调得比「识别完成立刻粘贴发送」更慢，并允许出现可恢复的错字。

目的是让这一会话里的打字和键鼠看起来像号的主人在操作，降低「整段瞬间出现」这种一眼失真。

1.0 对用户的承诺是：节奏可以配置，默认不是瞬间粘贴。1.0 不承诺微信或其他 IM 无法识别自动化，也不把「防检测成功」写成验收条件。

输入后端和节奏策略分开。软件键鼠是 1.0 的默认后端。USB 助理只作为可选后端，见 8.6。行为上的异常（全天在线、话术高度重复、短时间大量发送）不因更换输入后端消失。

自动化操作微信违反微信软件许可协议。产品内用一句常驻说明告知账号风险，不提供规避平台风控的操作教程。

## 4. 用户和要交的班

| 代号 | 用户 | 1.0 要替他值的班 | 他用来判断能不能用的事 |
|---|---|---|---|
| U1 | 有线上客资的本地生活商家。门店一个人看微信，问题集中在价目、地址、营业时间、能不能约 | 营业时间内答重复咨询。要下单、要改约、要投诉时交给店里的人 | 不报错价格，不把 A 客人的话记到 B 头上，晚上能看懂哪些对话必须自己接 |
| U2 | 做知识付费、自己维护私域的 KOL。语气本身就是产品 | 用他的语气答售前问题。课程内容以他放进本地知识包的资料为准 | 不像另一个人在说话，不编课程里没有的承诺，发送前他可以先看草稿 |
| U3 | 微商团队长。自己有一个微信号要维护，同时要管几十到上百人，没有时间守着输入框 | 这个号答重复问题。例外转给他。他回来用班报看这一班发生了什么 | 只占用他自己的这一个号。岗位包在本机，他离开键盘时例外找得到人 |

三类用户共用同一套客户端。差异落在智能体模板、知识包和节奏预设，不落在三套产品。

U3 的「几十到上百人」指他要管理的人，不是 1.0 要同时登录的微信账号数量。

## 5. 1.0 不做

以下各项有商业产品在做，1.0 明确不做。有人提出时，先回到第 3 节，而不是加功能。

- 主动触达、沉默唤醒、按客户阶段追消息。
- 全量群发、批量打招呼、自动加好友、自动评论朋友圈或帖子。
- 销售画像：价格敏感度、互动态度、核心阻塞点、每日运营报告式的销售复盘。
- 一台电脑同时跑多个 IM 或多个微信号。
- 微信、企业微信以外的平台适配。框选模式可以继续作为通用窗口的实验能力，不进入 1.0 验收。
- Coze、Dify、第三方工作流、开放视觉 API、SDK。
- 云端知识库、云端会话主库、企业任务下发、邀请码拆算力、子账号管理。
- 白牌打包、多品牌、兑换码自由定价、在线支付和会员中心。支付若要做，另立版本。
- 对话式生成智能体、每日自动改写提示词、自动更新知识库。
- 把「平台识别不到」作为卖点或验收项。

## 6. 现状基线

1.0 在现有桌面端上增量，不重写看屏主循环。

| 已有，1.0 复用 | 1.0 要补上的缺口 |
|---|---|
| 视觉定位微信、企业微信布局；像素规则找未读 | 会话级文字记忆 |
| 点击、输入、发送的主路径 | 默认发送改为可配置节奏，停止把整段粘贴当默认 |
| 鼠标移动已有曲线和点击按下抬起 | 打字过程本身仍是剪贴板一次粘贴 |
| 单个系统提示词 | 多个本地智能体，同时只启用一个 |
| 经验卡片，含人工纠正 | 点踩原因写入卡片；知识文件检索 |
| 工作轨迹、本地用量账本 | 面向号主的班报和会话状态 |
| Provider 插件，目前内置火山方舟 | 商业构建不把模型名露给前端；请求经网关 |
| 本地 skill server（start、pause、status） | 按会话暂停，而不只是全局暂停 |
| 打包构建可隐藏 token 费用 | 商业构建隐藏整块模型配置 |

Windows 的窗口分支存在，1.0 仍以 macOS 为验收平台。Windows 安装包不阻塞 1.0 收口，但节奏策略的接口不要写成只在 macOS 成立。

## 7. 版本切片

1.0 分成六刀。前一刀的验收没过，不开始下一刀里依赖它的功能。M0 是书面收口，和 M1 一起开始。

| 切片 | 用户得到什么 | 完成标准 |
|---|---|---|
| M0 切口 | 一份被遵守的边界 | 本文第 3 节和第 5 节评审通过。商业构建的界面清单上没有模型名 |
| M1 能离开屏幕的一班 | 有记忆、有闸门、能转人工、默认按节奏发送 | 用一份真实门店或 KOL 话术，连续处理一个晚上的咨询。不串会话，不秒回整段，该转的人能接到通知 |
| M2 本机脑子 | 资料在本地文件里，答不到就停 | 库里有的事实按库回答。库里没有的价格、地址、课程承诺不编造，并转人工 |
| M3 网关 | 商业包不暴露模型，按次数计费 | 更换网关后面的模型，界面和本地库都不用改。断网时本机记录仍能打开，只是不能新生成 |
| M4 完整节奏和素材 | 错字、手速、分段可按人设调节；当前会话可发固定素材 | 打开节奏后，录屏里一条三四十个字的回复是分段、有停顿、偶发改字的。关掉节奏才回到整段粘贴。问地址可以在当前会话发出事先指定的图片或文字 |
| M5 班报 | 号主回来五分钟内知道这一班该亲自接谁 | 班报能列出已回复、已转人工、未回复及原因。沉默联系人只出现在待处理队列，不会被自动发出消息 |

M1 之前，知识可以暂时写在提示词里。M2 之后，事实性内容以知识包为准，提示词只负责人设、语气和流程。

M3 放在回复质量之后。避免为一个仍会瞬间粘贴、仍会答错的当班去收费。

## 8. 功能需求

优先级只在所属切片内比较。P0 是该切片验收必需，P1 是该切片应有，P2 可滑到下一切片。

### 8.1 会话记忆（M1，P0）

按「当前会话的对方名称」保存文字回合。名称来自看屏结果。名称读不稳定时，这一轮不写入记忆，并在轨迹里记下「未绑定会话」，避免串话。

每条回合包含：时间、方向（对方 / 助手 / 人工）、正文、是否实际发出。

生成回复时带上该会话最近 20 条文字。20 是默认值，智能体上可改，范围 5 到 50。只带文字，不把历史截图再次送出。

用户可以查看某一会话的回合，并清空这一会话。清空不影响其他会话。

工作轨迹继续记录「为什么这么做」。回合记忆记录「说过什么」。两者不要并成一种数据。

### 8.2 回复闸门（M1，P0）

生成之前先过闸门。被闸门挡住时不发送，本地记下原因。

| 闸门 | 行为 |
|---|---|
| 无需回复 | 对方只是「收到」「好的」这类收束，或模型给出无需回复。不发送 |
| 冷处理 | 名称在冷处理名单里则不生成、不发送。原因记为「冷处理」。可以解除 |
| 黑名单 | 名称命中则永不回复。匹配前做去空白。支持精确名称 |
| 白名单模式 | 默认关闭。打开后只回复名单内的单聊 |
| 群聊 | 每个智能体二选一：回复全部群消息，或只回复 @ 到本号的消息。默认只回复 @ |

群聊 @ 的判断以看屏读到的文本为准。读不到 @ 关系时，按「只回复 @」的智能体这一轮不回复，并记录原因。

### 8.3 辅助模式和自动模式（M1，P0）

两种模式都走记忆、闸门和节奏策略。差别只在谁按下发送。

- 辅助模式：生成草稿，停在确认层。人可以编辑后发送，或丢弃。发送仍走当前节奏。
- 自动模式：闸门通过后，按节奏发送。

默认是辅助模式。从辅助切到自动时，用一句话说明账号风险，用户确认后生效。这一轮还要先点「核对当前窗口」：读到的名称置信，才允许打开自动发送。核对没有通过时，自动发送保持关闭。核对本身不写入会话记忆。

草稿上可以标记「这条有用」或「这条不行」。不行时必选一个原因：事实错误、语气不像、不该发、其他。原因写入经验卡片，下一次生成时注入。这条在 M1 做到能记，M2 与知识包一起验收「下次会避开」。

### 8.4 转人工（M1，P0）

触发后只暂停这一个会话，其他会话继续。

触发条件，全部可关：

- 用户词表：投诉、退款、报警，以及用户自己加的词。默认放投诉和退款。
- 同一会话连续两轮回复高度重复，或用户连续两次点「这条不行」。
- 知识库答不上事实性问题时。这项从 M2 起生效。
- 人在确认层点「转人工」。

暂停后的行为：

- 该会话不再自动发送。
- 向用户配置的一个地址发通知。1.0 支持企业微信群机器人或飞书自定义机器人的 Webhook，二选一即可。
- 通知内容只含对方名称、触发原因、时间。不附完整聊天记录。用户要看记录，回到这台电脑。
- 界面上这个会话显示「已转人工」，并有「恢复自动」。恢复只影响这一会话。

Webhook 失败时，会话仍然保持暂停。失败写在班报里，不能因为通知没发出去就继续自动回复。

### 8.5 真人节奏（M1 的 P0 子集，M4 补全）

节奏是智能体上的一组配置。发送、点输入框、发素材都读这一组。没有单独的「快速通道」。

M1 就要有的项：

| 配置 | 默认 | 说明 |
|---|---|---|
| 节奏开关 | 开 | 关掉后才允许整段粘贴并发送，供调试 |
| 阅读等待 | 开 | 开始打字前先停一小段，表示看过对方的话 |
| 长文分段 | 开 | 超过约两行的回复拆成多条发送，条与条之间停顿 |
| 打字方式 | 逐段输入 | 默认不再一次把整段放进输入框 |
| 上班时段 | 全天关、需用户设置 | 时段外只记录「时段外未回复」，不发送 |
| 每小时上限 | 30 条已发送回复 | 超过后这一小时剩余会话进入待处理，不发送 |

M4 补上的项：

| 配置 | 默认 | 说明 |
|---|---|---|
| 手速 | 自然 | 预设三档：稳、自然、慢。慢档给更长的阅读等待和分段间隔 |
| 错字 | 低 | 关 / 低 / 中。错字只来自常用近形或近音字，随后退格改正，再继续。不发送未改正的错字 |
| 错字范围 | 仅闲聊句 | 含数字、价格、地址、时间、链接的句子不错字 |
| 按智能体保存 | 是 | 门店和 KOL 可以不同手速 |

错字是表演给「像这个人在打」用的，改正后的正文必须等于模型给出的正文。不能把错字留在发出去的消息里。

验收只看用户可观察的结果：默认配置下，录屏中的长回复不是瞬间出现的整段；关闭节奏后，同一条回复回到一次放入。不验收「某平台的检测是否通过」。

### 8.6 输入后端（M4，P1）

用户看到的可选后端叫「USB 助理」。不使用「USB 键鼠」，也不使用「机器人」。

默认后端是现有软件键鼠。鼠标移动继续使用已有的曲线，点击保留按下和抬起。

可选后端是 USB HID（CH9329 一类设备）。1.0 只要求：

- 设置里出现「软件键鼠 / USB 助理」。
- 未插入设备时，USB 助理不可用，并说明当前仍用软件键鼠。
- 同一套节奏策略作用在两种后端上。
- 中文输入在 USB 后端可以用剪贴板粘贴，但粘贴的粒度服从分段和错字规则，不能退回「整段一次粘贴」。

HID 协议、接线和驱动以 `docs/usb-hid-ch9329-guide.md` 为工程笔记。该笔记不进入用户界面。云桌面没有物理 USB，设置里直接禁用 USB 选项。

若 M4 结束时软件后端的节奏验收已经通过，USB 后端可以保持可选、未插入不阻塞发版。

### 8.7 本地智能体（M2，P0）

一个智能体是一份本地岗位配置，包含：名称、提示词、知识包、黑白名单、群聊规则、转人工词表、Webhook、节奏、运行模式。

可以创建多个。同一时间只能启用一个。支持复制、停用、删除。删除前确认。删除智能体不删除已经产生的会话记录。

内置三份模板，用户可改：

| 模板 | 提示词侧重 | 默认模式 | 默认节奏 |
|---|---|---|---|
| 门店咨询 | 短句、先答事实、约时间和投诉交给人 | 辅助 | 自然 |
| 课程售前 | 保持作者语气、只讲资料里有的内容、购买方式用资料中的原句 | 辅助 | 慢 |
| 团队答疑 | 答重复的用法和发货问题、例外转人工 | 辅助 | 自然 |

1.0 不做「用一句话生成智能体」。模板加上可编辑的提示词就够。

### 8.8 本地知识包（M2，P0）

每个智能体绑定零个或一个知识包。知识包是本机的一组文件。

- 格式：Markdown、TXT、PDF。
- 上限：单个文件 10MB，一个知识包 30 个文件。超出时拒绝加入并说明原因。
- Word 文档不在 1.0。用户另存为 PDF 或 Markdown。
- 图片知识不在 1.0。要发出的图片走 8.9 的素材，不走检索。

检索在本机完成。1.0 使用本机关键词检索，把命中的少量段落注入这一次回复。不把知识包全文送到网关做向量化，也不上传原文。

两种回答方式：

- 直接答：不查知识包。用于寒暄和收束语。
- 查资料再答：先检索，再生成。事实性回答只能使用命中的段落和会话记忆里已经说过的话。

模型判断需要事实、但检索没有命中时，不生成猜测。这一会话转人工，原因是「资料里没有」。

用户可以在界面看到本次用了哪几个段落标题。标题来自文件名和段落小标题，方便他判断是不是答非所问。

### 8.9 当前会话素材（M4，P0）

素材是一条规则：当前会话的对方文本命中关键词时，发送预先指定的文字或本机图片。

- 只作用于当前打开的这一会话。
- 不搜索联系人，不遍历会话列表，不按标签群发。
- 发送过程走该智能体的节奏。
- 一条消息最多命中一条规则，按用户排列的顺序取第一条。
- 图片来自用户选择的本地文件。不读取微信收藏夹。

例子：命中「地址」发送地图图片；命中「多少钱」发送价目文字。价目文字建议同时放在知识包里，避免两个地方各写一版。

### 8.10 连接与网关（M3，P0）

客户端把推理看成两项能力，不看成某个模型。

| 能力 | 用途 | 商业版出口 |
|---|---|---|
| 看屏 | 布局、未读、当前会话文本 | 网关 |
| 回复 | 闸门之后的文字生成 | 网关 |

商业构建：

- 设置页没有供应商、模型名、Base URL、API Key。
- 用户登录的是 ChatBuddy 账号或许可证。1.0 用许可证兑换码激活即可，不做完整账号体系和子账号。
- 看屏不可用或回复不可用时，分两行说明。文案不出现上游厂商。
- 网关按许可证鉴权，并按看屏次数、回复次数记账。本地账本同步记一份，便于用户对账时导出。
- 网关不提供知识库同步接口，不提供会话上传接口。

开源构建：

- 保留现有 Provider 配置，供自己接 Key。
- 界面若必须显示当前 Provider，只出现在开源构建。商业构建用编译开关去掉，而不是运行时藏起来。

网关的服务端选择模型、失败时换备用模型，这些都不反映到客户端文案。客户端只区分：成功、额度用尽、网络不可用、服务暂不可用。

额度用尽时停止新的看屏和回复，本机已有记录只读可用。

### 8.11 班报和会话状态（M5，P0）

班报按自然日聚合，数据来自本机回合和闸门日志。

每个有过动作的会话只标三种状态：

| 状态 | 含义 |
|---|---|
| 待处理 | 看到了消息，但因为时段、上限、辅助模式未发送、或检索失败以外的原因没有发出 |
| 已转人工 | 8.4 已暂停 |
| 已处理 | 已发送，且没有待处理的新消息 |

班报列出：对方名称、状态、最后一条原因、最后动作时间。支持按状态筛选。支持把当日列表导出成一份本地 CSV。CSV 留在本机。

不做的字段：客户阶段、意向分、价格敏感度、互动态度。

沉默且当天没有新消息的联系人，不出现在班报里，也不会被生成一条追问。

### 8.12 冷处理（M1，P0）

冷处理是一份本机名单，用来让某些会话暂时不要 AI 接话。它不是黑名单。黑名单表示这个岗位永不回复；冷处理可以随时解除，解除后原来的回合还在，下一轮可以再回复。

名单的键和会话记忆相同：单聊或群，加上标题。群标题末尾的人数不进键。

加入方式只有两种：

- 当班窗口上的「冷处理当前会话」。只有这一轮已经确认对方是谁时才能点。
- 在当班页手工输入微信标题，并选择单聊或群。

检查发生在调用回复模型之前。命中后：不生成草稿，不发送，本地记下原因「冷处理」，把当前聊天画面记成已读基线，然后继续看下一条未读。取消冷处理不删除回合。

名称没读稳时，不写入记忆，也不生成回复。界面显示「还没确认当前会话是谁」。这一轮不猜一个名字去回复。

框选模式没有标题栏，整扇窗口共用一份「当前窗口」记忆。冷处理这扇窗口，就是停掉框选这条会话。

## 9. 界面结构

1.0 的主界面保持一个当班窗口，设置分四页。

| 页面 | 内容 |
|---|---|
| 当班 | 当前智能体、辅助或自动、本小时已发送数和上限、冷处理当前会话、核对当前窗口、开始和暂停 |
| 智能体 | 模板、提示词、知识包、闸门、转人工、节奏、素材规则 |
| 记录 | 会话回合、班报、经验卡片。商业构建的记录页不展示 token 费用 |
| 连接 | 商业构建：许可证、看屏状态、回复状态。开源构建：现有 Provider 表单 |

确认层（辅助模式）贴在当班窗口上，显示草稿、命中的资料标题、发送、丢弃、转人工、这条不行。

不在 1.0 增加运营看板、客户漏斗或模型选择器。

## 10. 数据放在哪里

| 数据 | 存放 | 是否进入网关 |
|---|---|---|
| 提示词、知识文件、检索索引 | 本机岗位包 | 否。回复请求只携带本次命中的少量段落 |
| 会话回合、班报、闸门日志 | 本机 | 否 |
| 经验卡片 | 本机 | 否。允许把卡片摘要放进当次回复请求 |
| 黑白名单、冷处理名单、节奏、素材规则 | 本机 | 否 |
| 当次屏幕画面 | 临时文件，识别后按现有轨迹策略保留在本机 | 是，仅当次看屏请求 |
| 当次要发送的正文 | 本机回合 | 生成时作为当次回复请求的一部分 |
| 许可证与次数 | 本机缓存一份，网关记一份 | 是 |
| Webhook 通知 | 用户自己的企业微信或飞书 | 只含名称、原因、时间 |

卸载时问用户是否保留岗位包。默认保留。

## 11. 成功标准

1.0 做完时，用同一套客户端可以完成下面三件事。每件事用真实账号做一次全程，而不是只看界面截图。

1. U1：把价目和地址放进知识包。辅助模式处理 10 条混合咨询。价格和地址与文件一致。一条退款消息停在转人工，店员收到通知。默认节奏下没有整段秒贴。
2. U2：用课程售前模板和一份课程介绍。人先看草稿再发送。资料没写的承诺不会出现在草稿里。手速设为慢档后，录屏能看出分段和停顿。
3. U3：只登录他自己的一个微信。自动模式在上班时段内回答知识包里有的重复问题，超过每小时上限后停止发送并进入待处理。当晚班报能在五分钟内指出必须亲自接的会话。

另外：把一个已经确认名称的会话冷处理之后，它的新消息不再生成、不再发送。取消冷处理后，回合还在，下一轮可以再回复。自动发送在「核对当前窗口」通过之前保持关闭。

商业构建另加一条：三件事的全程界面里，用户看不到模型名和供应商名；断开网关后仍能打开班报和知识包。

## 12. 风险和产品上的处理

| 风险 | 1.0 怎么处理 |
|---|---|
| 微信许可协议不允许自动化，账号仍可能被限制 | 默认辅助模式。切自动时确认。界面保留风险说明。不做群发和自动加好友，这两类最容易放大限制 |
| 用户期望「打开就能防检测」 | 文案和验收都只描述节奏。不把平台检测结果写成功能 |
| 看屏把会话名称看错，记忆串话 | 名称不稳定时不写入记忆，也不生成回复。界面显示没确认对方是谁。自动发送要等「核对当前窗口」通过 |
| 模型编造价格和承诺 | M2 起，事实问题无检索命中则转人工 |
| 知识包和素材各写一版价目 | 素材规则的说明里提示：事实以知识包为准，素材只负责发出那一段指定内容 |
| 网关被当成云端知识库来用 | 网关没有同步知识库和上传会话的接口。评审时按接口清单检查 |
| USB 方案被理解成消除封号 | 设置文案写明：它只更换输入设备，不改变发送频率和话术重复带来的风险 |
| Windows 与多显示器坐标偏差 | 1.0 验收平台定为 macOS 主屏。Windows 和副屏不写入完成标准 |

## 13. 开放问题

这些不影响 M1 开工。在对应切片开始前定下来即可。

1. 许可证的发放形式：一机一码，还是一码可在重装时迁移。M3 前决定。1.0 不做子账号。
2. 关键词检索如果在真实价目表上命中太差，是否在本机增加向量检索。允许加，前提仍是索引和原文不出这台电脑。M2 试用后再定。
3. 企业微信个人号与微信的看屏差异，是否在 M1 就一起验收。建议 M1 先验收微信单聊和群 @，企业微信作为同一闸门下的第二场景，不单独立项。
4. 商业包的产品名是否正式定为 ChatBuddy。代码里的界面文案已经是 ChatBuddy，安装包名仍是 SightFlow。M3 发商业包前统一一处。
